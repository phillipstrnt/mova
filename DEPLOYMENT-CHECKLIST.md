# MOVA POS production deployment checklist

This repository contains a React/Vite frontend (`client/`) and an Express/Mongoose API (`server/`). Suggested first deployment: Vercel for the frontend, Render for the API, and MongoDB Atlas for the database. Google OAuth and SMTP password recovery need separate provider setup. Do not put secrets in frontend `VITE_*` values; these are public build-time values.

## 1. Rotate the original secrets first

The original uploaded archive included `server/.env`. Treat every credential in that file as exposed: rotate the MongoDB database password, JWT signing secret, SMTP password, and any other tokens/keys present. Do not reuse them. The updated ZIP excludes that file and Git history. If any secret was committed to a remote Git repository, revoke/rotate it; deleting a file does not erase history.

## 2. MongoDB Atlas

1. Create a MongoDB Atlas project and production cluster.
2. Create a dedicated database user with access only to the MOVA database; use a unique generated password.
3. After the Render API service exists, open that service in Render and choose **Connect → Outbound**. Add every outbound CIDR shown there to Atlas under **Security → Network Access → IP Access List**. Render says a service may use any address in the listed ranges, so allow the full service range. The private address `192.168.56.1` is not a public Render egress address and cannot be used for this rule. For a local-only connection, use Atlas's **Add Current IP Address** from the same computer that runs the API.
4. Copy the `mongodb+srv://...` connection string privately. Use it as the Render `MONGO_URI` secret.
5. Enable backups and confirm TLS/network settings before storing real business data.

## 3. Deploy the API on Render

1. Push this sanitized project to a private GitHub repository you control.
2. In Render, create a new Blueprint and select the root `render.yaml` file. If Blueprint import is unavailable, create a Node web service with root directory `server`, build command `npm ci`, start command `npm start`, and health check `/api/health`.
3. Add the secret environment variables in Render's dashboard: `MONGO_URI`, `CLIENT_URL`, `APP_URL`, `GOOGLE_CLIENT_ID`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`. `JWT_SECRET` is generated by the Blueprint; verify it exists and is long/random.
4. `CLIENT_URL` is the exact deployed frontend origin (e.g. `https://your-app.vercel.app`). `APP_URL` is the same origin used to build reset links. No trailing slash or path; if you use a custom domain, update both.
5. Wait for deploy, then open `https://YOUR-API.onrender.com/api/health` and verify it returns HTTP 200 and a healthy JSON response.

## 4. Set up Google sign-in

1. Open Google Cloud Console and create/select a project.
2. Configure the OAuth consent screen with your app name and support email. Complete any verification steps required for your intended audience/scopes.
3. Create an OAuth Client ID of type **Web application**.
4. Add the frontend's exact origin (local development `http://localhost:5173` and the deployed Vercel origin) under **Authorized JavaScript origins**. This app sends an ID credential to the API; it does not need an OAuth redirect URI for the current Google Identity Services button flow.
5. Set the same Web Client ID in Render as `GOOGLE_CLIENT_ID` and in Vercel as `VITE_GOOGLE_CLIENT_ID`. Client ID is public; client secret, if Google shows one for the client, must never be added to `VITE_*` variables or committed to source.
6. Redeploy/rebuild after setting Vercel variables. Test existing Google account login and new Google account registration. New account flow requires business name and business type.

## 5. Set up email/password recovery

1. Choose an SMTP provider (transactional email provider recommended) and verify the sender/domain as required by that provider.
2. Configure the SMTP host, port, TLS setting, username, password, and verified sender address in Render environment settings. For port 587, `SMTP_SECURE=false` typically means STARTTLS; use the provider's documented values.
3. Set `APP_URL` to the deployed frontend origin. Password reset links point to `/reset-password/:token`.
4. After deployment, request a reset for a real account and verify the email arrives. Check provider delivery logs and Render logs without printing reset tokens or SMTP credentials. The UI/API intentionally use a generic response to avoid revealing whether an email is registered.

## 6. Deploy the frontend on Vercel

1. Import the repository into Vercel and set the project root directory to `client`.
2. Build command: `npm run build`; output directory: `dist`; install command: `npm ci`.
3. Add Vercel environment variables: `VITE_API_URL=https://YOUR-API.onrender.com/api` and `VITE_GOOGLE_CLIENT_ID=...`.
4. Deploy. The `client/vercel.json` rewrite supports React Router deep links such as `/register` and `/reset-password/...`.
5. Add the deployed Vercel origin to Google OAuth's authorized JavaScript origins and Render's `CLIENT_URL` / `APP_URL` as appropriate. Redeploy API and frontend after configuration changes.

## 7. Test the deployed application

Run the non-destructive API smoke tests from `server/`:

```bash
API_BASE_URL=https://YOUR-API.onrender.com npm run smoke:auth
```

On Windows PowerShell:

```powershell
$env:API_BASE_URL = "https://YOUR-API.onrender.com"
npm run smoke:auth
```

Then manually complete this end-to-end matrix in a browser:

- Register with a new email/password; confirm a single business and main branch are created.
- Sign in with the new credentials; wrong password and repeated attempts are rejected/rate-limited.
- Sign in with Google using an existing verified Google account.
- Register a new Google account and finish the business details form.
- Request password recovery; verify email arrives, reset once successfully, then confirm the same link cannot be reused.
- Confirm the old password fails and the new password succeeds; previously issued sessions should be invalidated by the API.
- Try expired/invalid reset links, an unverified/invalid Google credential, and protected routes while signed out.
- Check browser console and API logs for errors; verify all traffic uses HTTPS and CORS allows only the intended origins.

## 8. Seed trial data after deployment

The repeatable trial seed creates an isolated `MOVA Trial Market` business with Main and East branches, seven role-based users, eight products, 16 customers, 60 days of sales (60 per branch), 60 received purchases (30 per branch), inventory movements, nine weekly cashier schedules per cashier, and 120 closed cashier shifts (60 per branch). Product records point to bundled client image assets. It does not modify other businesses. Run it only against the intended trial database after verifying the exact database name:

```powershell
cd server
$env:MOVA_ENABLE_TRIAL_SEED = "true"
$env:MOVA_TRIAL_SEED_CONFIRM_DB = "YOUR_EXACT_DATABASE_NAME"
npm run seed:trial
```

The script generates one random password for the seven trial accounts and prints it after a successful seed. Set `MOVA_TRIAL_PASSWORD` first if you need a known shared trial password. Share the printed credentials only with intended testers, and remove or rotate the trial accounts before using the database for real business data.
